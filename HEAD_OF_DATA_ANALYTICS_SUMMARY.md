# Vessel KPI Monitoring and Data Correction — Summary for the Head of Data Analytics

**Objective.** The prototype gives operations analysts a single place to review vessel Power and Speed performance against the supplied baseline KPIs, investigate flagged observations, and correct report values with a traceable record of changes.

**Approach.** I built a Python Dash application with Plotly scatter charts for Power % and Speed % over report timestamps. Vessel, date range, KPI, and voyage type filters are applied consistently across the charts, headline counts, and report detail table. Filter-flag values distinguish flagged observations from unflagged ones. Analysts can use box or lasso selection on either chart to narrow the table to the underlying report rows; with no selection, the table displays all rows in the current filter scope. Negative deviation values are highlighted in red to make underperformance easier to spot.

**Data quality and control decisions.** The source contains one row per KPI reading, so blanks for the other KPI's fields are expected and are not treated as errors. The app explicitly watches for missing Power % on Power rows, duplicate Report_ID values, and negative Speed % readings. Because Report_ID is not unique in this file, the app assigns an internal row key to distinguish rows and avoid updating the wrong record. Inline edits are limited to Power % and Speed %. Before saving, the backend checks that values are numeric, between 0 and 200, consistent with the row's KPI, and not blank for the active KPI. Accepted changes are persisted in SQLite and written to an audit log with the report identifier, field, old and new values, user, and UTC timestamp.

**Key design decision.** SQLite provides a lightweight local stand-in for a production Delta Lake upsert, making saved corrections persist across app restarts rather than remaining only in browser memory. The supplied filter flags and deviations are displayed as provided; they are not automatically recalculated after a correction because the business rules for recalculation were not included in the exercise brief.

**Recommended next phase.** For production, I would move persistence to Delta tables, implement a `MERGE` using a stable source-system key, and store audit events in a separate governed table. I would add role-based access, mandatory correction reasons, concurrency handling, automated tests, and a remediation workflow for flagged data-quality issues. I would also agree and document the business rules for recomputing deviations and anomaly flags after edits, then validate the application with operations analysts before wider rollout.
